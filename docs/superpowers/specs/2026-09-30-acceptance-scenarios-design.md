# 验收场景套件设计

日期：2026-09-30　状态：待实现

## 目标

一条命令回答"uvrpc 能不能真拿来用"：跑完全部场景，全绿才算可用。

## 位置与职责

`tests/acceptance/`，独立目录，注册进 ctest，label `acceptance`。

`examples/` 保持纯演示，不动。两者职责分离——示例今天证明了演示会腐烂（4 个示例编译不过却没人发现），
所以验收不能复用示例，示例也不能替代验收。

## 为什么是"跨度不变性"而不是"跑通"

现有 16 个测试已经确认覆盖：五个传输各自的基线、服务端重启后的重连、5 客户端扇出、
传输先退先关、流式、注册表契约、分配器归属、DSL 生成代码、超时清扫。

这些证明的是**存在性**——每条路能通。它们无法发现**两条路不一致**，而跨度问题的本质就是不一致。

所以核心断言是：

> 同一份应用逻辑跑遍 5 个传输，断言可观测行为完全一致。
> 传输只该改变速度，不该改变结果。

## 已查实的跨度漏洞

`uvrpc_request_t::client_ctx` 是公开字段，头文件写的是
"Client context for sending response (from UVBus)"，而它的实际类型按传输不同：

|传输|第 3 参（`client_ctx`）|
|---|---|
|TCP / IPC / INPROC / SAMELOOP|客户端句柄|
|UDP|`sockaddr *`|

框架内部是自洽的（`uvrpc_server.c:451,486` 用 `uvbus_send_to(..., req->client_ctx)`，
而每个传输的 `send_to` 期望的正是自己存进去的东西），所以**库自己的回包路径没问题**。
有问题的是公开字段：文档邀请应用去用它，而它换个传输就是另一个类型。
拿它回包的代码在 TCP 上能跑，换 UDP 就传错指针。

验收套件要把这件事钉住：要么各传输统一，要么在头文件明确"禁止直接使用，回包只用
`uvrpc_request_send_response()`"。**倾向后者**——强行统一要在传输层加抽象，代价大于收益。

## 场景清单

只收**现有测试没覆盖、且出问题时最致命**的场景。已覆盖的不重复。

### A 组　协议健壮性（远程攻击面，现有零测试）

对端发来畸形数据时不能崩、不能越界读。今天已有真实先例：今天修掉的崩溃里，
有一个就是 `method` 为 NULL 时传给 `HASH_FIND_STR` 导致 `strcmp(NULL)`，**远程可触发**。

|场景|断言|
|---|---|
|截断帧（长度前缀大于实际载荷）|不崩溃，返回错误或忽略，不越界读|
|垃圾字节（非本协议帧）|不崩溃|
|空方法名|不崩溃（`HASH_FIND_STR` 键为 NULL 的老路径）|
|伪造超大长度前缀（声称 1GB，实发 10 字节）|不分配超大缓冲区|
|半截 header|不崩溃|

### B 组　背压与限流（文档声称三种无锁拒绝，零测试）

`RATE_LIMITED` / `CALLBACK_LIMIT` / `TRANSPORT_BUSY` 三个错误码可区分，这点比多数库好，
但没有测试锁住它。槽位泄漏是最隐蔽的 bug。

|场景|断言|
|---|---|
|并发配额耗尽|返回 `RATE_LIMITED`，且不发出任何一帧|
|路由槽位被占|返回 `CALLBACK_LIMIT`|
|传输写队列满|返回 `TRANSPORT_BUSY`|
|**恢复后槽位归还**|超时/失败后配额计数归零，能继续发起|

### C 组　在途生命周期（UAF 的真实形态）

现有 `test_transport_lifetime` 只测了**顺序释放**，没测**在途时释放**——而后者才是 UAF 的真实形态。

|场景|断言|
|---|---|
|请求在途时 `uvrpc_client_free`|不 UAF（ASan job 覆盖）|
|请求在途时 `uvrpc_server_free`|不 UAF|
|请求在途时释放 registry|不 UAF|

### D 组　负载边界（阈值有明确定义才有测试价值）

默认 64KB、硬上限 1MB。

|场景|断言|
|---|---|
|零长度载荷|正常往返|
|变长序列（0 → 1MB 递增）|结果字节与输入一致|
|刚超 64KB 默认上限|行为符合声明|
|接近 1MB 硬上限|行为符合声明|

### E 组　失败模式（真实系统一定会碰到）

|场景|断言|
|---|---|
|服务端未启动时 connect|返回错误而非挂死|
|未知方法|返回可区分错误|
|对端中途关闭|不崩溃，pending 正确收敛|

### F 组　跨度不变性（核心）

同一份应用逻辑，五个传输各跑一遍，**跨传输比对结果**，而不是各自断言成功。

|断言|能抓住什么|
|---|---|
|回包用 `uvrpc_request_send_response()`，五传输行为一致|`client_ctx` 类型分歧|
|服务端 `send` 与 `broadcast` 语义五传输相同|今天修掉的 SAMELOOP 段错误|
|错误码在五传输上对应同一失败|背压/断线的分类差异|
|同一负载在五传输上服务端看到的字节相同|编解码/分帧差异|

**UDP 那一格是例外**，且必须例外：UDP 必然丢包，这不是 bug。所以那一格断言的是
**"丢包不得静默消耗共享资源"**——响应持续丢失时，槽位必须按超时归还，
而不是累积到 `RATE_LIMITED`。（`tests/call_timeout_test.c` 已覆盖这一格的机制部分。）

## Harness 契约

`acceptance/harness.h` 提供：

- 建 server/client（含 registry），统一构造顺序
- 注册 handler
- 断言宏，失败时打印**期望值 vs 实际值**
- **看门狗**：每个用例强制有超时，杜绝挂死
- 统一收尾

看门狗不是可选项。今天 `test_transport_lifetime` 空转了很久还打印 OK——
没有超时的测试等于没有测试。

## 通过判据

- 每个用例失败时打印"期望 X，实际 Y"并非零退出
- **任何用例不得挂死**，看门狗超时即失败
- `ctest -L acceptance` 一条命令出总判
- CI 现有的 default-allocator 与 custom-allocator 两个 job 自动覆盖

## 明确不做

- 不做 benchmark（归 `benchmark/`）
- 不重写现有测试
- 不做表驱动笛卡尔积——选"每场景一个文件"，可读性和可调试性更重要
- 不修 `client_ctx` 类型分歧本身——本套件只负责暴露它，修不修是下一个决策
